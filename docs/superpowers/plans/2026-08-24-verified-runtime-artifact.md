# Verified Runtime Artifact Implementation Plan

## Goal

Replace production DSH runtime installation through local npm with a verified,
platform-specific runtime artifact pipeline. The Desktop updater must observe
upstream npm metadata for diagnostics, compare installed versions only against
the verified artifact index, download and hash-check a ZIP, reject unsafe
archives, validate the extracted runtime with the existing verifier, and keep
the existing promotion, rollback, external-process ownership, pending-update,
and restart semantics.

The current branch is `codex/dsh-runtime-updater`. This plan deliberately does
not merge to `main` or claim a release gate until the real artifact, Desktop
E2E, packaging, NSIS installation/update, restart persistence, rollback, and
full regression evidence exist.

## Architecture and Constraints

- `NpmRegistryUpdateSource` remains an upstream observation and diagnostics
  source. Its version is named `upstreamLatestVersion` and is never used as the
  production update target.
- `VerifiedRuntimeUpdateSource` reads a signed-by-publishing-process,
  machine-readable `runtime-index.json`; this implementation validates the
  schema, target `win32-x64`, package name, exact SemVer, artifact URL, byte
  size, SHA-256, and manifest URL/data.
- `VerifiedRuntimeArtifact` is the single validation boundary for index
  entries and `runtime-manifest.json`. It rejects wrong platform/architecture,
  missing identity fields, malformed hashes, invalid sizes, and mismatched
  package/version identity before any install operation.
- `RuntimeArtifactDownloader` streams to
  `staging/<operation-id>/artifact.zip.part`, closes and renames only after a
  successful transfer, verifies byte count and SHA-256, validates every ZIP
  entry before extraction, and extracts only below the operation staging root.
  It removes partial files and failed extraction directories.
- ZIP entry validation rejects absolute paths, drive-qualified paths, `..`
  traversal, and any resolved destination outside the extraction root. The
  downloader must never overwrite the active runtime.
- The existing `DshRuntimeManager`, `RuntimeStateStore`,
  `HarnessProcessManager`, `HarnessHealthChecker`, and `verifyRuntime()` remain
  the authorities for runtime identity, state transitions, process ownership,
  health, and CLI verification. The update manager receives an artifact
  preparation dependency instead of invoking `NpmInstaller` in production.
- `prepare-bundled-runtime.js` consumes an already-built verified artifact and
  performs the same manifest/CLI/Web/health/native smoke checks. It must not
  resolve or install DSH from a live registry during `npm run pack` or `npm run
  dist`.
- No automatic fallback to npm is allowed in the application default wiring.
  The legacy `NpmInstaller` remains testable and available only for explicit
  development/diagnostic injection.
- All new behavior is implemented test-first. Focused tests must be run after
  each red/green slice, followed by the complete `npm test` suite.

## Implementation Tasks

### 1. Freeze artifact contracts with failing tests

Files:

- Add `test/verified-runtime-artifact.test.js`.
- Add `test/verified-runtime-update-source.test.js`.
- Add `test/runtime-artifact-downloader.test.js`.

First add tests that currently fail for:

- valid `runtime-index.json` selection of `win32-x64`;
- rejection of a missing SHA-256, invalid byte size, invalid SemVer, wrong
  package, wrong platform, wrong architecture, and an artifact URL that is not
  an absolute HTTP(S) URL;
- exact manifest identity (`@deepseek-ai/dsh`, version, `win32`, `x64`) and
  normalized entrypoint metadata;
- rejection of `../evil`, `/absolute/file`, `C:\\absolute\\file`, and a
  normalized path escaping the extraction root;
- downloader success with exact bytes and hash, hash mismatch, byte mismatch,
  HTTP error, timeout, and cleanup of `.part` files.

Use injected HTTP/request and ZIP adapters in unit tests so the tests are
deterministic and do not contact a registry. Include at least one real ZIP
fixture generated by the test helper or a checked-in minimal fixture for the
successful extraction/`verifyRuntime()` contract.

Run the new focused files and record the expected red result before adding
production modules.

### 2. Implement manifest and index validation

Files:

- Add `src/runtime/verified-runtime-artifact.js`.
- Add `src/update/verified-runtime-update-source.js`.

Implement small pure functions with stable error codes/messages:

```js
const artifact = VerifiedRuntimeArtifact.fromIndexEntry(entry, {
  platform: process.platform,
  arch: process.arch,
});
const latest = await source.getLatest({ platform: 'win32', arch: 'x64' });
```

The returned object must include `packageName`, `version`, `platform`, `arch`,
`artifactUrl`, `sizeBytes`, `sha256`, and a manifest reference or validated
manifest. `getLatest()` must select only the requested target and fail closed
when there is no exact target entry. It must not silently select a different
platform, architecture, package, or dist-tag.

Add source tests for malformed JSON, HTTP status failures, and deterministic
selection of the highest explicitly published verified version (the source
must not query npm or infer versions from a package registry response).

Run the focused contract tests to green.

### 3. Implement streaming download and safe ZIP extraction

Files:

- Add `src/update/runtime-artifact-downloader.js`.
- Add or update `package.json` and `package-lock.json` to declare the chosen
  ZIP reader as a production dependency.

The downloader API should be explicit and injectable:

```js
const prepared = await downloader.prepare({
  artifact,
  stagingRoot,
  operationId,
});
// prepared.rootPath is the extracted runtime root for verifyRuntime().
```

Stream response bodies to disk while updating a crypto SHA-256 hash and byte
counter. Write only to `.part`; rename after the response completes and the
HTTP status, byte count, and hash all match. Use an operation-specific
directory and a timeout. Validate all archive names before extraction, create
directories with `mkdir`, and ensure each resolved output path remains under
the extraction root. Do not follow archive-provided symlink/hardlink targets.

The returned root must contain `runtime-manifest.json` and the DSH CLI layout
expected by `DshRuntimeManager`/`verifyRuntime()`. Failed downloads, hashes,
unsafe entries, and extraction errors must leave the active runtime untouched.

Run downloader, security, and cleanup tests to green.

### 4. Integrate verified source into update orchestration

Files:

- Update `src/update/dsh-update-manager.js`.
- Update `src/lifecycle/app-lifecycle.js`.
- Update `src/update/update-state.js` or the existing state snapshot only if
  needed to preserve explicit field names.
- Add/update `test/dsh-update-manager.test.js`,
  `test/dsh-runtime-update-integration.test.js`, and
  `test/app-lifecycle-update-flow.test.js`.

Add explicit dependencies for `upstreamSource`, `verifiedSource`, and
`artifactDownloader` while retaining compatibility for tests that inject the
legacy registry/installer. Production lifecycle wiring must create the
verified source and downloader and must not construct `NpmInstaller` as the
update preparation path.

Make check snapshots distinguish:

```js
{
  upstreamLatestVersion,
  verifiedLatestVersion,
  installedVersion,
}
```

Use `verifiedLatestVersion` for the update comparison. On confirmation, call
the downloader, then the existing verifier, then the existing promote/activate
flow. Keep failed update behavior, external ownership, pending activation,
rollback, and restart state persistence unchanged.

Add a regression test that injects an installer which throws if called and a
working artifact downloader; the update succeeds without an npm installer
call. Add a test proving an npm observation newer than the verified index does
not trigger an unverified update.

Run all update/lifecycle focused tests to green.

### 5. Convert bundled-runtime preparation to artifact consumption

Files:

- Update `scripts/prepare-bundled-runtime.js`.
- Update `test/prepare-bundled-runtime.test.js`.
- Add a small fixture/config helper under `test/fixtures/runtime-artifacts/` if

Replace the current live `npm install` default with an explicit artifact input
(`DSH_VERIFIED_RUNTIME_ARTIFACT`, a configured artifact path, or the checked-in
release fixture used by the packaging pipeline). Validate the artifact
manifest, extract it into a temporary build directory, verify CLI identity,
launch `dsh web`, run the existing real HTTP health checker, and run the

checks pass; swap atomically and clean temporary output.

Retain an explicitly injected legacy install function only for old unit tests
or development diagnostics, and make the default script fail with a clear
message when no verified artifact is supplied. This ensures `pack`/`dist` do
not hide a registry install.

Run the preparation tests and a local fixture-based bundled-runtime smoke.

### 6. Add Runtime Factory artifact assembly and self-verification

Files:

- Add `scripts/build-verified-runtime-artifact.js`.
- Add/update `test/runtime-factory-artifact.test.js`.
- Update `docs/runtime/dsh-runtime-factory-evaluation.md` with the exact
  reproducible command and provenance fields.

The script must accept an immutable DSH source revision, Node/pnpm versions,
target platform/arch, and output directory. It must build with the frozen
lockfile, assemble a portable runtime tree without junctions or unresolved
workspace links, write `runtime-manifest.json`, create a ZIP, calculate size
and SHA-256, and emit an index entry. Before success it must extract the ZIP to
an independent temp directory and run the CLI, Web/Health, and native smoke
checks against the extracted artifact itself. It must fail if the archive is
missing files that existed in the assembled root.

The script must not publish or overwrite a release index unless self-smoke and
manifest/hash checks pass. The first Route B archive failure is retained as
negative evidence; only a complete artifact self-smoke can advance the gate.

Run the factory script against the previously validated rc.7 source fixture or
an equivalent immutable source checkout, then use the resulting ZIP for the
bundled-runtime and updater integration tests.

### 7. Validate real Desktop behavior and packaging

Files/tests:

- Add/update integration tests for real artifact download, restart
  persistence, rollback, external process ownership, and pending activation.
- Update `docs/runtime/dsh-runtime-update-verification.md` with commands,
  artifact SHA-256, and observed results.
- Update `docs/runtime/dsh-runtime-release-gate.md` and
  `docs/runtime/dsh-runtime-install-blocker-root-cause.md` only with verified
  evidence.

Run, in order:

1. the complete unit/integration suite;
2. real extracted-artifact CLI/Web/Health/native smoke;
3. Desktop update from a local HTTP artifact server with hash and partial
   failure cases;
4. restart persistence, rollback, external ownership, and pending activation;
5. `npm run prepare:bundled-runtime` using the verified artifact;
6. `npm run pack` and `npm run dist`;
7. NSIS install, installed-app update, restart, and rollback smoke.

Do not call the release gate PASS unless every required evidence row is
complete and the final diff/test review finds no production npm install path.

## Self-review Before Execution

- No task depends on an unapproved product decision; the artifact architecture
  and Route B direction are approved by the task brief.
- Every production file change has a named test or a documented packaging/E2E
  command.
- The legacy npm modules are explicitly constrained to diagnostics/test
  injection and are not silently used by application defaults.
- Archive validation is performed before extraction and artifact hash/size are
  checked before promotion.
- The plan preserves current process ownership and state-machine behavior.
- The previously observed failed ZIP attempt is treated as a blocker to
  release evidence, not as a successful artifact.

## Execution Order

Execute tasks 1–3 as a TDD slice, then tasks 4–5 for Desktop integration, then
task 6 for reproducible factory output, and finally task 7 for release-gate
verification. After each slice run its focused test command and show the
result before proceeding.
